### 821ea7ce5 fix(deploy): the master release check must accept a 401 from the registry
- 意图：`curl -f` 在 401 时丢弃状态码并以非零退出，导致对「行为完全正确的 registry」报 NOT REACHABLE；去掉 `-f`。
- 改动：`deployment/tokeness-cn/release-on-master.sh:36-38`（当时）：`curl -fsS` → `curl -sS`，`-w '%{http_code}'` 的输出仍由 `grep -qE '200|401'` 判定。
- 官方基线对比：`fork-only` — 证据：上游无该文件；`git show upstream/main:Dockerfile | grep -i curl` 无命中，上游无 registry 探针逻辑。
- 契约：registry 可达性探针必须把 HTTP 401（Docker v2 API 未认证的标准应答）计为可达；只有超时/网络错误才报 NOT REACHABLE。
- 证据（测试/符号）：无测试；符号 `check()` 中的 curl 探针。
- 事故/背景：在入口机实跑 `--check` 时被手工探针（已显示 401）当场抓到——假阴性会让可用环境被误判为不可用并阻断发版。
- 迁移处置：**必须实现（作为语义）**——任何对 Docker registry 的可达性探测都必须接受 401，这是协议事实，丢了会重演假阴性阻断。

### fe8a2f738 fix(release): do not pin every build to a mainland proxy; restore VERSION (M3, M4)
- 意图：M3——ab7fa4c73 把 GOPROXY 默认改成 goproxy.cn 会连带影响共享该 Dockerfile 的 CNB 管线（配额恢复后），把默认还给 Go 官方 proxy，大陆加速由 release-local.sh 显式传 `--build-arg`；M4——VERSION 是构建产物且残留在工作树，「one 'git add -A' away from being committed」，脚本退出时恢复它。
- 改动：`Dockerfile.tokeness:33`（现）`ARG GOPROXY=https://proxy.golang.org,direct`；`release-local.sh:114-116` `restore_version()` + `trap restore_version EXIT`；`release-local.sh:124` 增加 `--build-arg "GOPROXY=${GOPROXY:-https://goproxy.cn,direct}"`。
- 官方基线对比：`fork-only` — 证据：上游 Dockerfile 无 GOPROXY（grep exit 1）；上游把 VERSION 作为**受跟踪文件**直接 `COPY ./VERSION`（`git show upstream/main:Dockerfile:7`），从不在构建时改写它，因此「构建时写 VERSION + 退出恢复」这条契约上游完全没有。
- 契约：共享 Dockerfile 的 GOPROXY 默认必须是 Go 官方值，大陆加速只由显式传参的构建持有；脚本无论成败退出后 VERSION 必须回到 HEAD 内容（失败可见后果：不恢复则源树被一个构建产物污染）。
- 证据（测试/符号）：无测试；符号 `restore_version`、`trap ... EXIT`。
- 事故/背景：M3/M4 是复审编号，非生产事故数字；风险是「差点把构建产物提交进库」。
- 迁移处置：**建议**——「默认值不因特例构建而全局改变」与「构建产物不得留在源树」是通用卫生契约；具体到自研网关取决于其 VERSION 注入方式。

### b30a22490f fix(release): confirm the digest with the registry before deploying (M2)
- 意图：脚本此前把**本地** RepoDigests（本机 push 的记录）交给 deploy.sh 写进缩容配置；现改为从 registry 读回 manifest digest 并比对，不一致拒绝发版——「deploying an artifact nobody can identify」。
- 改动：`release-local.sh:147-155`（现）：`docker buildx imagetools inspect --format '{{json .Manifest.Digest}}'` 读回 registry 侧 digest，与本地值不等则 `die`；读不到则 WARNING 且本地值记为 unverified。
- 官方基线对比：`fork-only` — 证据：上游无该脚本；上游 Dockerfile 与发版链路（GitHub Actions）中无 `imagetools`/digest 对账逻辑（`grep -i digest upstream/main:Dockerfile` 无命中）。
- 契约：push 成功后必须以 registry 确认的 manifest digest 作为部署凭据；本地与 registry 不一致 → 拒绝发布（退出非零、无 rollout）；读不到 → 显式 WARNING 而非静默放行。
- 证据（测试/符号）：release-local.sh 本身无测试；但 deploy.sh 侧的 digest 固定行为有测试——`deployment/tokeness-cn/tests/deploy-test.sh`（`release-certified-digest` 用例，L573-589，验证显式 digest 必须原样 pin、mutable tag 不得通过校验）。
- 事故/背景：M2 复审项；已在 `ml-...mainland.44` 上实测两边一致（非事故数字）。
- 迁移处置：**必须实现（语义）**——「部署凭据必须是 registry 自己确认的 digest」直接防「部署了无法识别的制品」；丢了会在多机/代理场景重演 digest 漂移。

### 0e71a879e fix(release): prove pull authorisation, pick a real cache source, honour --no-cache (M1, L1)
- 意图：M1——`--check` 只证 registry 可达与缩容组可读，不证本机**能拉镜像**（发版第一个真正撞上的失败）；`--check <tag>` 现在用本机 docker 凭据实际读一次 manifest。L1——缓存源原是「docker images 里第一个 ml-*」，可能是毫不相关的分支构建；改为最高版本号的 release tag，回退任意 ml-*；`--no-cache` 还要传给 docker build，否则 BuildKit 自身缓存仍会短路。
- 改动：`release-on-master.sh:52-70`（现）`--check <tag>` 增加 `docker manifest inspect` 拉取授权检查，无 tag 时输出 NOTE 说明只验了可达性；`release-local.sh:94-106` 缓存源按 `mainland.N` 数字取最高；`release-local.sh:121-128` `USE_CACHE=0` 时改传 `--no-cache` 给 docker build。
- 官方基线对比：`fork-only` — 证据：上游无这两个文件；上游构建环境（GitHub Actions + Dockerfile）无缓存源选择与 pull 授权预检逻辑。
- 契约：`--check <tag>` 必须以本机凭据真实读一次 `ml-<tag>` manifest，失败即非零退出；无 tag 时输出必须明示「仅验证可达性」；缓存源默认是本地最高版本 release tag；`--no-cache` 必须同时去掉 `--cache-from` 并传 `--no-cache`（否则 BuildKit 缓存仍命中）。
- 证据（测试/符号）：无测试（`grep 'no-cache\|manifest inspect' deployment/tokeness-cn/tests/` 0 命中）；符号 `docker manifest inspect`、`cache_args`、`USE_CACHE`。
- 事故/背景：M1/L1 复审项，无事故数字。
- 迁移处置：**建议（M1 拉取授权预检为「必须实现」候选）**——「发版前证明本机真的能拉镜像」与 821ea7ce5 的 401 语义同族，是防「rollout 起跑即失败」的廉价门禁；缓存源选择与 --no-cache 属构建性能细节，可弃用。
