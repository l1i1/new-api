# G03 · pin/拟合「候选耗尽」必须可证明 + 饱和豁免
- 范围：`c66ed310e`、`9653d6975`、`24ddf1e56`、`d992051da`、`99abc4dde`
- 上游基线：upstream/main @ 42e694eb6（QuantumNous/new-api）
- 结论摘要：这 5 个提交是同一缺陷（「从 `ChannelSelectionTemporarilyUnavailable` kind 反推候选耗尽」这个不可靠推断）的多轮整改链，最终形态 = ①专用 kind `ChannelSelectionUnprovableExhaustion`（区别于 temporarily_unavailable / internal_selection_error）＋ ②分类器在 pin/拟合路径拒绝该推断且对饱和走查豁免 ＋ ③controller 有 last upstream error 时透传真实上游裁决、不写 `retry_no_candidate` ＋ ④video 能力查询失败按错误上报而非吞成空集 ＋ ⑤`retryFoundNoPinnedCandidate`（pin 前置判据）与饱和豁免的回归测试。上游**完全没有**这条错误语义契约（无 `classifyChannelSelectionFailure`、无 `retry_no_candidate` 记录、无 video 能力过滤器、无保真守卫），全部属 fork-only；但上游 DB 路径 `GetChannel` 是"先过滤后分层"（model/ability.go:107-148），不存在 fork 修的那个"先分层后过滤"缺陷形态，迁移时应把这条当作**自研网关自身的证据纪律**而非上游兼容。迁移建议：错误语义部分**必须实现**（防"替上游编理由"），pin/拟合宿主部分随 fit/pin 产品能力决定。

## 1. 逐提交档案

- 契约：当重试选路失败且错误码为 `get_channel_failed` 时，**仅当**官方拟合 pin 在场、无饱和走查、且 kind 为可证明的"无候选"时才写 `retry_no_candidate` 并可用上游旧裁决作答；无 pin/饱和/其他 kind 时客户保持路由错误本身，不写该标记。

## 2. 组内关系
同一缺陷（"从可用性探测/空集反推候选耗尽"）的四轮整改 + 一条防回归测试，**链式递进、后者替代前者的中间形态**：
1. `c66ed310e`：判据加 pin 前置（`retryFoundNoPinnedCandidate`），但默认路径仍产 temporarily_unavailable；
2. `9653d6975`：堵住 video 过滤器吞 DB 错误这个旁路（错误传播）；
3. `24ddf1e56`：堵住 DB 预筛旁路——分类器在 pin/fit 路径直接拒绝该推断（中间形态：返回 InternalError）；
4. `d992051da`：把中间形态升级为最终形态——专用 kind `unprovable_exhaustion` + 真实上游裁决透传 + 饱和豁免；
5. `99abc4dde`：钉住 d992051da 的饱和豁免，防回归。
**最终形态 = d992051da（语义）+ 99abc4dde（验收）**；c66ed310e 的 `retryFoundNoPinnedCandidate` 与 9653d6975 的错误传播仍是最终形态的组成部分（controller 判据与 video 路径），未被替代。
