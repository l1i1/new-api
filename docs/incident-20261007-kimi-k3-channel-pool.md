## 二、失败形态与根因链

最早的失败（16:30–17:30，共 157 条）：

```
ch37  41 次  status_code=503, 服务繁忙，请稍后重试。
ch48  38 次  status_code=502, 服务繁忙，请稍后重试。
```

其余为客户端问题（输入超长、Responses API 不支持），量很小。17:30–18:30 出现 `524`（网关超时）。

推断的链条：

1. 16:40 前后 ch48、ch37 上游开始返 `服务繁忙`（502/503）；
2. 失败率爬升，重试把流量往剩余渠道挤压；
3. 18:20 翻过半数，池子过载；
4. 挤压之下 ch19、ch49 额度被打穿（21:02 读到 `¥-38.98` 与 `＄-44.78`）；
5. 20:00 后 ch11 也垮；
6. 峰值 90%；
7. 充值 + 摘除死渠道后恢复。

第 4 步是从负余额倒推的，**没有直接证据说明它何时变负**（需上游账单时间），此处如实标注。

## 三、诊断中确认的两件事（含一次误判更正）

**重试机制本身是好的。** 一条请求的完整轨迹：

```
a1 ch48 → failure → retry_keyword_matched
a2 ch37 → failure → retry_keyword_matched
a3 ch19 → …
成功落在 ch49（19:11:07，耗时 70 秒）
```

尝试号递增、渠道在换。**曾经把"三条失败日志行各自携带同一份策略快照"误读为"同一渠道重试三次"**，此处更正。

**重试次数 11–20 是策略条目数，不是上游调用次数。**两条条目 = 一次干净调用（`attempt/channel_selected` + `success/request_completed`）。故障期的 11–20 条 ≈ 5–10 次调用，与 `RetryTimes = 6` 相符。

## 四、真正的配置缺陷

```
AutomaticDisableChannelEnabled = false        ← 自动摘除渠道的总开关，关着
AutomaticDisableStatusCodes    = 401
AutomaticDisableKeywords       = 13 条，全英文
```

两个问题：

1. **总开关关着**，所以渠道不管失败多少次都留在轮换里，并按优先级永远排在前面 —— 每个请求都要先撞一遍死渠道，这是 70 秒延迟的来源。
2. **禁用关键字表里没有中文欠费词**。当天报错是 `403 用户额度不足, 剩余额度: ¥-38.98`，而表里只有 `insufficient balance` —— **即使开关开着，ch19/ch49 也不会被摘掉**。

机制细节（读代码确认）：`ChannelDisableThreshold = 5` 只用于渠道测试；**中继路径是"一条错误即禁用"**，没有连续失败缓冲；禁用仅对渠道自身 `auto_ban=1` 生效，而 **52 条渠道全部为 1**。

第二次（修正）：

| 键 | 最终值 | 理由 |
|---|---|---|
| `AutomaticDisableKeywords` | **12 条，全部终态** | 移除 `upstream response failed`、`Our servers are currently overloaded` —— 瞬时状况应触发换渠道，不应摘渠道 |
| `AutomaticDisableChannelEnabled` | `true` | 保留：这是本次真正要修的 |
| `AutomaticEnableChannelEnabled` | **`false`（回到原值）** | 定时渠道测试 `monitor_setting.auto_test_channel_enabled = false`，恢复路径不会触发，该开关是空转的；且终态原因（欠费）本就需要人工恢复 |
| `AutomaticDisableStatusCodes` | `401` | 未动（凭证失效属终态） |

最终禁用词表：`Your credit balance is too low` / `This organization has been disabled.` / `You exceeded your current quota` / `The security token included in the request is invalid` / `Your account is not authorized` / `insufficient balance` / `insufficient account balance` / `额度不足` / `余额不足` / `剩余额度` / `账户余额不足` / `欠费`。

**回滚**：把备份文件里的四个键写回即可（`PUT /api/option/`，`{key,value}`）。

## 七、遗留风险与未决

1. **单点依赖**：ch19 一条承载 780/791。它再出事就是全盘。
2. **无自动恢复**：`auto_test_channel_enabled=false`，被摘渠道需人工放回。这对终态原因是对的，但意味着**误摘也要人工发现**。
3. **全量 auto_ban**：52 条渠道都开了 auto_ban；禁用表已收紧到终态词，风险可控，但仍需观察 12–24 小时有无误摘。
4. **ch48 / ch37**：手动停用中，上游 502/503 的原因未查，修好前不要放回。
5. **ch11 / ch1**：失败原因未查（账号 or 上游），恢复还是永久停用待定。
6. **33 条手动停用渠道**：占 52 条中的 33 条，未审查。
7. **发现机制**：已加 `scripts/kimi-k3-watch.sh`（20 分钟阈值检查，阈值 5%，静默运行）。但它依赖会话活着；**真正的无人值守告警需要平台 token 可被定时器读取**，这是凭据决定，待用户拍板。

## 八、教训

1. **巡检间隔不能跨过整个事故。** 4 小时一轮的检查，其窗口落在事故前 40 分钟与峰值上，中间 4 小时 20 分无人知晓。已改为 20 分钟阈值检查。
2. **"翻代码"和"读日志"都会看错，要用单条请求的完整轨迹下结论。** 本文第三节的误判就是这样产生的：三条日志行 ≠ 三次重试。
3. **改一个开关之前，先确认它的另一半在不在。** 打开 `AutomaticEnableChannelEnabled` 时没有检查 `auto_test_channel_enabled`，结果开了一个空转的开关，并据它向用户做了错误承诺。
4. **启用一项机制时，要为它原有的配置负责。** 总开关关着时，禁用词表里的瞬时性词无害；一旦打开，它们就变成"一次上游抖动永久摘掉一批健康渠道"。启用前必须先审词表。
