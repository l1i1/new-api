## 三、诊断中确认的两件事（含一次误判更正）

**重试机制本身是好的。** 一条请求的完整轨迹：

```
a1 ch48 → failure → retry_keyword_matched
a2 ch37 → failure → retry_keyword_matched
a3 ch19 → …
成功落在 ch49（19:11:07，耗时 70 秒）
```

尝试号递增、渠道在换。**曾经把"三条失败日志行各自携带同一份策略快照"误读为"同一渠道重试三次"**，此处更正。

**重试次数 11–20 是策略条目数，不是上游调用次数。**两条条目 = 一次干净调用（`attempt/channel_selected` + `success/request_completed`）。故障期的 11–20 条 ≈ 5–10 次调用，与 `RetryTimes = 6` 相符。

## 四、真正的配置缺陷

```
AutomaticDisableChannelEnabled = false        ← 自动摘除渠道的总开关，关着
AutomaticDisableStatusCodes    = 401
AutomaticDisableKeywords       = 13 条，全英文
```

两个问题：

1. **总开关关着**，所以渠道不管失败多少次都留在轮换里，并按优先级永远排在前面 —— 每个请求都要先撞一遍死渠道，这是 70 秒延迟的来源。
2. **禁用关键字表里没有中文欠费词**。当天报错是 `403 用户额度不足, 剩余额度: ¥-38.98`，而表里只有 `insufficient balance` —— **即使开关开着，ch19/ch49 也不会被摘掉**。

机制细节（读代码确认）：`ChannelDisableThreshold = 5` 只用于渠道测试；**中继路径是"一条错误即禁用"**，没有连续失败缓冲；禁用仅对渠道自身 `auto_ban=1` 生效，而 **52 条渠道全部为 1**。

## 八、教训

1. **巡检间隔不能跨过整个事故。** 4 小时一轮的检查，其窗口落在事故前 40 分钟与峰值上，中间 4 小时 20 分无人知晓。已改为 20 分钟阈值检查。
2. **"翻代码"和"读日志"都会看错，要用单条请求的完整轨迹下结论。** 本文第三节的误判就是这样产生的：三条日志行 ≠ 三次重试。
3. **改一个开关之前，先确认它的另一半在不在。** 打开 `AutomaticEnableChannelEnabled` 时没有检查 `auto_test_channel_enabled`，结果开了一个空转的开关，并据它向用户做了错误承诺。
4. **启用一项机制时，要为它原有的配置负责。** 总开关关着时，禁用词表里的瞬时性词无害；一旦打开，它们就变成"一次上游抖动永久摘掉一批健康渠道"。启用前必须先审词表。

**在把某个组件放进关键路径之前，没有先让它在一个小到不会伤人的位置上被验证过。**

## 十二、整夜演进（2026-10-07 22:00 → 2026-10-08 10:00）：ch19 耗尽，主力三跳

§9 预言的结局按时发生，而且**没有砸到人**。

### 12.1 ch19 耗尽并被自动摘除

ch19 在 **01:0x 前后**退出服务，之后 10 分钟窗口里归零。它的 `status` 变成 **3**（自动禁用），
不是人工操作 —— 这正是 §5 新增的终态禁用词起了作用：上游返余额错误 → 命中关键字 →
`AutomaticDisableChannelEnabled=true` 生效 → 摘除。**这是当晚改动第一次在真实故障上生效。**

### 12.2 主力三跳，每一步都能归因

按 30 分钟窗口统计 kimi-k3 的渠道分布：

| 时段 | 失败率 | 主力 | 触发原因 |
|---|---|---|---|
| 21:08 | 74.90% | ch49 70% / ch19 30% | 事故恢复中 |
| 21:38–23:38 | 0.71%–5.02% | **ch19 73%–99%** | 当晚最佳窗口 |
| 00:08 | 3.50% | ch49 60% / ch74 40% | ch19 开始退场 |
| 00:38 | 4.83% | ch48 62% | 用户启用 ch48 |
| 01:08 | 1.30% | ch48 40% / ch37 37% / ch75 20% | 用户启用 ch37 与 ch75 |
| 01:38–10:00 | **0.10%–0.35%** | **ch37 59%**（另 ch75 34%、ch8 7%） | 绑定漂移收敛 |

**机制**：会话绑定的 TTL 是 1 小时，一个对话"第一次成功落在哪"就钉在哪一小时，
所以**改优先级不会立刻重排存量对话，只会改变新对话的去向** —— 渠道更替必然是渐进的。
实测漂移曲线与该机制完全吻合，因此**没有清缓存**（清了会一次性失掉全部上游前缀缓存）。

### 12.3 关键结论：绑定是"每对话一条"，不是"每 token 一条"

§5 的规则改动（`conversation_prefix`）在本夜上线并验证：

| 指标 | 改动前 | 改动后 |
|---|---|---|
| 3,553 次请求 | 1 条绑定 | — |
| 357 次请求 | — | **47 条绑定** |
| 后续窗口 | — | 131 条绑定 |

随后用采样功能抓了 **5 条 cdp-kimi 真实请求**做判定性检验：

```
前缀指纹 5 个 / 请求 5 条   ⇒ 它们本来就是不同对话，没有被塌缩成一个键
（内容各不相同：16 条消息的 tool 链、单轮"请介绍一下你自己"、Lean file-prover 任务、
  <system-reminder> 长 system、以及一条空 messages）
```

⇒ 对**这波流量**，"集中到某条渠道"**不是键塌缩造成的**，而是绑定集合的
「过去一小时时间平均」+ 优先级档位共同决定。用户最初观察到的 "都钉 ch48" 是
采样观感：实际该 token 在 30 分钟里是 ch48 47% / ch37 33% / ch75 15% / ch74 5%。

## 十五、仍未解决的技术问题：chi-y-u 的 504 卡死

本夜唯一持续存在的失败类，且形态与前面几种完全不同：

```
15–17 条/小时,全部 ch74/ch75(同一上游 chi-y-u,一个走 SOCKS5 代理、一个直连)
is_stream = False        ⇒ 响应从未提交给客户
elapsed   = 600038 ms    ⇒ 上游自己的 600 秒上限,不是网关设的
           (RELAY_TIMEOUT 默认 0 = 不限;RELAY_RESPONSE_HEADER_TIMEOUT = 1800)
策略轨迹  = attempt=1 → failure(504) → stop / reason=status_not_retryable
```

**同一种请求在 ch37/ch48 上 11–35 秒答完** ⇒ 不是"这活儿要十分钟"，是 **chi-y-u 卡住了**。
客户等 10 分钟然后拿到错误，是本夜体验最差的一类。

**为什么"把 504 加进重试名单"是错的**：504 不在 `AutomaticRetryStatusCodes`
（`409-503,505-599`）里，也不在 `NeverRetryStatusCodes`（线上为空）。但平台**没有按渠道的超时**
（`channel:response_time_exceeded` 只在渠道自检路径使用），而 `RetryTimes = 6` ⇒
若每个渠道都挂 600 秒，客户可能等 **1 小时**才拿到错误，比现在更糟。
全局超时旋钮（`RELAY_TIMEOUT`/`STREAMING_TIMEOUT`）是容器 env、要重启、且影响所有模型 ——
当晚就有正常请求跑了 247 秒，设 120 秒会把它一起砍掉。

**可行的两条路**（待用户定）：① 让上游修（同请求在别处 11 秒完成，是他们的卡死）；
② 给代码加"按渠道的请求超时"，超时即以可重试的 `channel:response_time_exceeded` 失败 ⇒
既保住 chi-y-u 的性价比（优先级不动），又把"等 10 分钟"压到"最多几分钟后换渠道成功"。
