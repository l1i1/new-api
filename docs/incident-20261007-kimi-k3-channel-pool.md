## 二、失败形态与根因链

最早的失败（16:30–17:30，共 157 条）：

```
ch37  41 次  status_code=503, 服务繁忙，请稍后重试。
ch48  38 次  status_code=502, 服务繁忙，请稍后重试。
```

其余为客户端问题（输入超长、Responses API 不支持），量很小。17:30–18:30 出现 `524`（网关超时）。

推断的链条：

1. 16:40 前后 ch48、ch37 上游开始返 `服务繁忙`（502/503）；
2. 失败率爬升，重试把流量往剩余渠道挤压；
3. 18:20 翻过半数，池子过载；
4. 挤压之下 ch19、ch49 额度被打穿（21:02 读到 `¥-38.98` 与 `＄-44.78`）；
5. 20:00 后 ch11 也垮；
6. 峰值 90%；
7. 充值 + 摘除死渠道后恢复。

第 4 步是从负余额倒推的，**没有直接证据说明它何时变负**（需上游账单时间），此处如实标注。

## 三、诊断中确认的两件事（含一次误判更正）

**重试机制本身是好的。** 一条请求的完整轨迹：

```
a1 ch48 → failure → retry_keyword_matched
a2 ch37 → failure → retry_keyword_matched
a3 ch19 → …
成功落在 ch49（19:11:07，耗时 70 秒）
```

尝试号递增、渠道在换。**曾经把"三条失败日志行各自携带同一份策略快照"误读为"同一渠道重试三次"**，此处更正。

**重试次数 11–20 是策略条目数，不是上游调用次数。**两条条目 = 一次干净调用（`attempt/channel_selected` + `success/request_completed`）。故障期的 11–20 条 ≈ 5–10 次调用，与 `RetryTimes = 6` 相符。

## 四、真正的配置缺陷

```
AutomaticDisableChannelEnabled = false        ← 自动摘除渠道的总开关，关着
AutomaticDisableStatusCodes    = 401
AutomaticDisableKeywords       = 13 条，全英文
```

两个问题：

1. **总开关关着**，所以渠道不管失败多少次都留在轮换里，并按优先级永远排在前面 —— 每个请求都要先撞一遍死渠道，这是 70 秒延迟的来源。
2. **禁用关键字表里没有中文欠费词**。当天报错是 `403 用户额度不足, 剩余额度: ¥-38.98`，而表里只有 `insufficient balance` —— **即使开关开着，ch19/ch49 也不会被摘掉**。

机制细节（读代码确认）：`ChannelDisableThreshold = 5` 只用于渠道测试；**中继路径是"一条错误即禁用"**，没有连续失败缓冲；禁用仅对渠道自身 `auto_ban=1` 生效，而 **52 条渠道全部为 1**。

| 键 | 最终值 | 理由 |
|---|---|---|
| `AutomaticDisableKeywords` | **12 条，全部终态** | 移除 `upstream response failed`、`Our servers are currently overloaded` —— 瞬时状况应触发换渠道，不应摘渠道 |

**回滚**：把备份文件里的四个键写回即可（`PUT /api/option/`，`{key,value}`）。

## 八、教训

1. **巡检间隔不能跨过整个事故。** 4 小时一轮的检查，其窗口落在事故前 40 分钟与峰值上，中间 4 小时 20 分无人知晓。已改为 20 分钟阈值检查。
2. **"翻代码"和"读日志"都会看错，要用单条请求的完整轨迹下结论。** 本文第三节的误判就是这样产生的：三条日志行 ≠ 三次重试。
3. **改一个开关之前，先确认它的另一半在不在。** 打开 `AutomaticEnableChannelEnabled` 时没有检查 `auto_test_channel_enabled`，结果开了一个空转的开关，并据它向用户做了错误承诺。
4. **启用一项机制时，要为它原有的配置负责。** 总开关关着时，禁用词表里的瞬时性词无害；一旦打开，它们就变成"一次上游抖动永久摘掉一批健康渠道"。启用前必须先审词表。

## 十、处置过程中我自己造成的第二次事故（2026-10-07 22:0x）

**我做错了什么**：为缓解 ch19 余额将尽，我把四条**从未承过量的**候选渠道（ch20/38/39/40）
**一次性启用，并把优先级直接提到与主 carrier 同级（148）**。

**为什么错**：同优先级意味着均衡器**立刻把真实流量摊给它们**，而不是"先溢出、再试探"。
这四条此前的全部履历是 **各 6 笔内部测试请求**（token 名 `ops-safe-202`，10-05 用 6/6 通过，随后一直停用）。
单发 6 笔能过，不代表能承量。

**后果**（启用后约 5 分钟）：

| 渠道 | 成功 | 失败 | 失败原因 |
|---|---|---|---|
| ch20 DEF_kongji | 19 | **8** | `502 Service temporarily unavailable. Please check your API key` |
| ch38 DEF_APlink-B | 2 | **3** | — |
| ch39 DEF_APlink | 18 | 0 | 唯一干净 |
| ch40 DEF_Tongba-Tokens | 7 | **7** | 50% 失败 |

全站 kimi-k3 失败率被抬到约 8.5%。**用户当场手动停用了它们**（ch38 由当晚新开的终态自动禁用规则摘除，status=3）。

**已收尾**：四条优先级已还原为原值（ch20/38/40 → 49、ch39 → 40），状态为停用；实测流量已回到 ch19，
失败率回落至 1.09%。**留下一个陷阱已被拆除**：若只停用而不还原优先级，日后任何人启用它们都会立刻冲到最前。

**正确的做法应当是**：

1. **一次只动一条**，不要四条一起；
2. **优先级压在现役主力之下**（如 147 或更低），让它只接溢出流量，而不是与主 carrier 平分；
3. 观察足够长的窗口（不止 5 分钟）确认成功率与 p50 稳定，再考虑下一条；
4. 尤其注意：**"单发测试通过"与"能承量"是两件事**，后者只能在低优先级下、用真实流量小步验证。

**这是当晚第二个由我造成的问题**（第一个是 §五 的空转开关与错误承诺）。两次的共性都是：
**在把某个组件放进关键路径之前，没有先让它在一个小到不会伤人的位置上被验证过。**

### 关键判据（本次最重要的方法教训）

**单发探活通过 ≠ 可用。**四个候选（ch20/38/39/40）单发全过，上量即崩；
ch37 更是 **13 次单发全过，启用后 61% 失败**。唯一可信的判据是**放进真实流量里、在不会伤人的位置上观察**。

**"能跑"与"划算"是两件事。**ch8（2,009 元历史、784ms）与 ch41（1,303 元）是池内最快的两条，
但成本上亏本，长期被有意压在优先级 1–2。**优先级编码了经济性**，不应从低优先级里挑接盘方。

### 当前局面

- **ch19 是唯一"快且可用"的渠道**，而其上游号池正在耗尽，充值无法解决；
- ch49 / ch4 可用但慢一倍以上；
- 池内**没有第三条能接主力的渠道**；
- ⇒ 出路只有两条：**引入新的上游号源**（业务侧），或 **ch19 耗尽后接受降级**（p50 从 16s 变 51s）。
  后者不是故障，但客户可感知。

### 已就位的防护

1. 20 分钟一次的失败率阈值检查（`scripts/kimi-k3-watch.sh`，阈值 5%）；
2. ch19 耗尽时会返回 `403 用户额度不足`，命中当晚新增的终态禁用词 ⇒ 被自动摘除，
   流量按优先级落到 ch49（优先级 147，仅次于 ch19 的 148），**不会砸进死渠道**；
3. ch4（优先级 66）排在 ch49 之后，因其仍有 503，不宜提前。
