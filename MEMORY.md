# New API Fork Memory

- This repository is the Tokeness-maintained fork of `QuantumNous/new-api`. The default integration branch is `tokeness/main`; `origin` is `l1i1/new-api` and `upstream` is read-only.
- Tokeness production images are built from `Dockerfile.tokeness`, published to GHCR, and deployed by immutable digest through the staged four-node workflow. Do not deploy mutable tags or bypass the production approval environment.
- The canonical frontend is `web/`. Tokeness-specific UI work must be implemented in the React source and built into the application image, not injected into compiled HTML by Nginx or a CDN-hosted script.
- The historical injected frontend lives outside this repository under `tools/nginx-dev-proxy` and its independent `repo-newapi-webdist` repository. It remains a rollback reference while the native migration is in progress.
- Dynamic administrator-authored content uses the compact Tokeness localization syntax `<tnt l="zh">...</tnt>`. Localization belongs at explicit display boundaries and must not mutate arbitrary API responses or install global fetch/XHR/DOM hooks.
- `<tnt>` resolves one adjacent translation group at a time using active language, English, then Chinese fallback. Invalid, duplicate, nested, unsupported, and unclosed tags remain raw; the legacy `<tokeness-text>` tag and language-keyed JSON are intentionally unsupported.
- Native `<tnt>` display boundaries include home/about/legal/footer, notices and announcements, FAQ/API information, model descriptions, wallet/payment/subscription copy, chat preset names, and `UserUsableGroups` descriptions. Editors, API caches, chat URLs, group IDs, ratios, payment IDs, and request payloads always retain raw values.
- Interface language code `zhTW` must survive browser-detector cache reloads and map to document/Intl locale `zh-TW`. Home metadata owns localized SEO on `/` and restores the configured system name on SPA navigation. Localized TanStack accessor rows must be invalidated when the language changes so visible sorting is not stale.
- Wallet add-funds amounts are always presented in CNY regardless of the global quota display type. Preset/top-up credit values convert system USD with the configured USD-to-CNY rate, while payable and savings values remain the backend-calculated CNY amounts and receive formatting only. Do not restore the historical client-side payment formula.
- Production deployment treats both previous and target images as trusted immutable GHCR digests. A node result is successful only after final runtime-image, state, health/status, and version checks; interruption and ambiguous SSH results participate in idempotent rollback.
- The production rollout job reserves 240 minutes for the complete forward and reverse transaction. After an ambiguous SSH result, rollback reconciliation waits for the remote lock and repeatedly verifies or restores the preflight digest within a 20-minute per-node budget; transaction tests cover full-fleet success, CDN-triggered reverse rollback, and lock-release recovery.
- The native Tokeness public header exposes language, theme, and navigation controls at mobile widths. Browser acceptance must keep the language switch reachable at 390 px and confirm no horizontal overflow after changing languages.
- The mobile public-header language entry is protected by a component test that finds it through the navigation-menu control group, opens the real language menu, changes the active language, and verifies the opt-out prop removes both desktop and mobile entries.
- Real-browser acceptance on 2026-07-27 confirmed that isolated administrator HTML is rendered through a Shadow DOM after DOMPurify removes scripts, event attributes, and event handlers. Happy DOM is not treated as equivalent security evidence.
- Production `HomePageContent` is empty. The React-native Tokeness home is the only home-page source of truth; do not restore placeholder content or Nginx/CDN CSS and JavaScript injection.
- Never store production credentials, private keys, API keys, database connection strings, or secret values in this file or the repository.

- Channel `used_quota` increments must remain direct atomic database writes. Tokeness runs multiple New API processes against one database, so per-process batch buffers can replay pre-reset deltas and make an operator-cleared counter reappear. The `/channels` reset operation therefore reads and clears the channel under one database row lock; consume logs remain the historical billing source of truth.

- Pricing vendors keep `Vendor.Name` as the canonical unique identity used by model sync, filters, URLs, counts, and colour seeds. Localized vendor labels belong in the optional `Vendor.DisplayName` field using `<tnt>`; `/api/pricing` exposes both fields and the frontend localizes only at display boundaries. Never put `<tnt>` in the canonical vendor name because exact-name sync would create duplicates.

Production `v1.0.0-rc.21-tokeness-localization.1` renders the Chinese and English labels correctly on a fresh dashboard load. - The native wallet keeps backend-calculated payment amounts. Its custom amount row may show the configured CNY base-price multiplier as an explanatory label, but the payable amount must always come from the backend calculation and be formatted as CNY without conversion. Standard EPay keeps the payable row and redirect reminder in the confirmation dialog; Stripe, Waffo, Waffo Pancake, and Creem omit that row because their checkout owns settlement display. The affiliate card matches historical `home.js`: it states the automatic 20% first-top-up reward, shows only invite count and referral link, and omits pending/history balances and manual transfer because native settlement credits ordinary inviter quota directly.
- The wallet referral card now reads the authenticated user's native invite-reward ledger through `GET /api/user/invite-topup-rewards`. The endpoint is self-scoped, cache-disabled, paginated, and returns only server-owned program/rate metadata, applied/pending/skipped summary counts, applied-only reward total, and sanitized reward status items. The UI keeps the historical link/copy flow, displays completed first-top-ups, total CNY-equivalent rewards, processing count, and recent statuses with independent loading, empty, and retryable error states. It never renders invitee identity, order/provider data, base top-up amount, `aff_quota`, or transfer controls.
- Native invite first-top-up rewards use `top_ups.credited_quota` plus the `invite_top_up_rewards` database outbox. EPay, Stripe, Creem, Waffo, and Waffo Pancake create one pending event inside settlement; payout to ordinary inviter quota is atomic with ledger status and retries through a master-node system task. The feature is fail-closed unless `INVITE_FIRST_TOPUP_REWARD_ENABLED=true` and an explicit `INVITE_FIRST_TOPUP_REWARD_START_TIMESTAMP` are shared by every node. Stop and audit the legacy Tokeness Ops cron before enabling it; never infer that legacy `pending`/`failed` JSON entries are unpaid.
- User creation must persist `InviterId` in both `Insert` and OAuth `InsertWithTx`. Registration-time rewards alone are not a durable invitation relationship and cannot support later first-top-up settlement.
- Tokeness home metadata is localized at the React home-route boundary and restored on SPA navigation. `web/index.html` carries the English Tokeness title, description, keywords, Open Graph, and Twitter fallback for crawlers while preserving the New API generator attribution.

- Waffo Pancake's production `MerchantProvidedBuyerIdentity` is the customer's email, not the synthetic `new-api-user-{userID}` value. Rejecting a signed `order.completed` webhook on that comparison and then returning HTTP 200 creates permanent pending orders. Settlement validation should use merchant external order ID, provider, amount, and currency, or compare against an identity snapshot persisted when checkout is created; retryable failures must not be acknowledged as successful delivery.
- EPay callback processing must be one idempotent database transaction covering row locking, provider and amount validation, top-up status, `CompleteTime`, and user quota. Return literal `success` only after commit; return a retryable failure otherwise. Administrator completion must reconcile the provider's paid order first and detect already-credited or mismatched orders, because delayed notifications and incorrect order IDs can otherwise produce duplicate credit.
- EPay administrator reconciliation rejects the configured public payment host after normalizing DNS case, trailing dots, and IP spelling. Literal private/loopback origins remain valid over HTTP or HTTPS for Docker-local production paths; every other HTTPS origin requires an exact `EPAY_RECONCILIATION_ALLOWED_HOSTS` entry. Do not add wildcard, suffix, URL, or port matching because the merchant key is sent in the query string.
- Payment webhooks should not share the general dashboard/API IP bucket. Apply a dedicated provider/path limiter and retain a pending-order reconciliation job as the recovery path for missing or exhausted callbacks.
- Payment callback routes are registered before `GlobalAPIRateLimit` and use independent `PW:<path>` source-IP buckets (300 requests per 60 seconds), so provider retries cannot consume or be rejected by the interactive API bucket. A master-node scheduled `payment_reconciliation_scan` records aggregate counts and oldest timestamps for external top-ups pending beyond 30 minutes every 15 minutes and emits a warning without changing order or wallet state. Automatic settlement remains intentionally blocked until each provider has a verified paid-state query and amount/currency validation path.
